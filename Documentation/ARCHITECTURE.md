# MacPulse Architecture

## Overview

MacPulse is a native macOS 14+ app written in Swift 6 and SwiftUI. Code is split into
Swift Package targets with one-way dependencies. The Xcode app target (generated by
XcodeGen from `project.yml`) contains only the `@main` entry point.

```
                ┌───────────────────────┐
                │  MacPulse.app          │  App/MacPulseApp  (@main, Window, Commands)
                └──────────┬────────────┘
                           │
                ┌──────────▼────────────┐
                │  MacPulseAppCore       │  App/Core — composition root
                │  RootView, Coordinator │  AppDependencies, SidebarSection
                └───┬──────────────┬─────┘
                    │              │
      ┌─────────────▼───┐    ┌─────▼──────────────────┐
      │ MacPulseFeatures │    │ MacPulseInfrastructure  │
      │ Views + VMs      │    │ IOKit, libproc, FS, ... │
      └───┬──────────┬───┘    └───┬────────────┬───────┘
          │          │            │            │
          │    ┌─────▼────────────▼──┐         │
          │    │ MacPulseShared       │         │
          │    │ UI, Utilities, Log   │         │
          │    └─────────┬────────────┘         │
          │              │                      │
      ┌───▼──────────────▼──────────────────────▼──┐
      │ MacPulseDomain                              │
      │ Models, Repository protocols, Use cases,    │
      │ Policies — Foundation only                  │
      └─────────────────────────────────────────────┘
```

| Target | Path | May import |
|---|---|---|
| `MacPulseDomain` | `Domain/` | Foundation |
| `MacPulseShared` | `Shared/` | Domain, SwiftUI, OSLog |
| `MacPulseInfrastructure` | `Infrastructure/` | Domain, Shared, Darwin, IOKit, … |
| `MacPulseFeatures` | `Features/` | Domain, Shared, SwiftUI |
| `MacPulseAppCore` | `App/Core/` | everything above |

**Rule:** Features never import Infrastructure. A view model receives Domain protocols
through its initializer; `AppDependencies` decides which implementation backs them.

## Presentation (MVVM)

- Each screen is a SwiftUI `View` plus a `@MainActor @Observable` view model.
- View models expose state (`LoadState<T>`, `Metric<T>`) and async intents (`load()`).
- `RootView` creates view models once, so switching sections keeps their state.
- Previews and UI tests use `AppDependencies.preview()` (launch argument
  `-MacPulseUseFakeServices`), never real hardware.

## Value honesty: `Metric<T>` and `MetricProvenance`

Every number shown to the user is a `Metric<T>`:

| Provenance | Meaning | Badge |
|---|---|---|
| `.measured` | Read directly from a supported macOS API | green "Measured" |
| `.estimated(basis:)` | Derived; `basis` explains how | orange "Estimate" |
| `.unavailable(reason)` | No trustworthy value; never shows a number | grey "Unavailable" |

`Metric` can only be built through `measured`/`estimated`/`unavailable`, so an
unavailable metric cannot carry a value. `MetricValueView` renders the value, the badge,
a tooltip explanation and VoiceOver hint.

## Concurrency

- Swift 6 language mode with complete strict-concurrency checking.
- View models and navigation are `@MainActor`.
- Repository protocols are `Sendable` and `async`; implementations do their work off
  the main actor. Long-running services (samplers, scanners) will be `actor`s with
  cooperative cancellation (Phases 2–6).

## Errors and logging

- `AppError` is the only error type that reaches the UI: a `kind`, a displayable
  `userMessage` and an optional `technicalDetail`. `AppError.wrapping(_:userMessage:)`
  classifies Foundation/POSIX errors.
- `Log.logger(_:)` returns an `os.Logger` per category (subsystem
  `com.mrismail.MacPulse`). Paths and process names are interpolated as private;
  file contents are never logged.

## Testing

| Suite | Location | Runs |
|---|---|---|
| Unit | `Tests/UnitTests/*` | `swift test` (Swift Testing) |
| Integration | `Tests/IntegrationTests/*` | `swift test`, against the real machine |
| UI automation | `Tests/UIAutomationTests/` | Xcode ⌘U / `xcodebuild test` (XCUITest, fake services), also in CI |

CI (`.github/workflows/ci.yml`, macOS runner, on PRs and `main`) builds the package with
warnings as errors, runs unit + integration tests, generates the Xcode project, builds
the app and runs the UI tests, checks the Release build has no entitlements and the Hardened Runtime, launches
the app for 10 seconds and builds the Release configuration.

## Battery monitoring (Phase 2)

```
IOKitBatteryProbe ──raw──▶ BatteryReadingBuilder ──BatteryReading──▶ BatteryMonitor (actor)
 (Infrastructure)            (Domain/Policies)                         │   every 60 s + on IOPS events
                                                                       ├─▶ JSONLinesBatteryHistoryStore (append)
                                                                       ├─▶ RuntimeEstimator (recent discharge)
                                                                       └─▶ AsyncStream<BatteryStatus> ──▶ Overview, Battery screen
```

- `AppModel` (App/Core) is created once by `MacPulseApp`. It owns the coordinator and
  every screen's view model, shared by the main window, the Settings window (⌘,) and
  menu commands, and starts `BatteryMonitor`.
- Sampling uses `Task.sleep(for:tolerance:)` with 10 s tolerance so macOS can coalesce
  wake-ups. Samples are serialized; power events inside 5 s get one trailing sample
  (ADR-006).
- The estimator window is in memory; the Battery screen loads history on range change
  only and appends live samples. `ChargingSessionDetector` and
  `BatteryHistoryChartModel` (gap-aware, ≤ 400 points) run off the main actor.
- `BatteryStatusPresentation` is the single source of state wording and the
  "Estimated runtime" definition; `BatteryRecommendations` drives the Overview.
- History is only recorded while MacPulse runs. A background agent / menu-bar
  companion is planned for Phase 7.

## Energy / battery drain detection (Phase 3)

```
LiveProcessSnapshotSource ──ProcessSnapshot──▶ ProcessMonitor (actor)
 sysctl + proc_pidinfo + proc_pid_rusage         │ 60 s background / 10 s while Energy is visible
 (current user's processes only)                 ├─▶ ProcessActivityCalculator (deltas by pid + start time)
                                                 ├─▶ AppUsageAggregator (helpers → app, estimated impact)
                                                 ├─▶ DrainAlertEvaluator (sustained CPU, battery-only)
                                                 ├─▶ UsageHourAccumulator ─▶ JSONLinesAppUsageStore (hourly, 7 days)
                                                 └─▶ AsyncStream<EnergyStatus> ─▶ Energy, Battery card, Overview
```

- CPU time is converted from Mach ticks with the timebase (ticks ≠ ns on Apple silicon).
- A process is identified by pid **and** start time; reused pids and counters that go
  backwards never produce activity. Intervals across sleep (> 3 min gap) are skipped.
- MacPulse excludes itself from the ranking and reports its own CPU in every status.
- Root/system processes are counted ("N system processes aren't included"), never read.
- Battery impact is always an estimate (ADR-011).
